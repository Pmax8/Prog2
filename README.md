# Text-to-SQL with a local LLM

A web application that answers questions about a movie database written in plain language.
A local Large Language Model (Gemma 3, served by [Ollama](https://ollama.com)) translates each question into a SQL query,
the backend checks that the query is read-only, runs it on MariaDB and returns the results.
If the generated query fails, the app sends the database error back to the model and asks it to correct the query on its own.

> University project (Sapienza University of Rome). The course project was designed for teams of 2–3; I designed and built every component on my own.

## Features

- **Natural-language search.** Ask *"Quali film ha diretto Christopher Nolan dopo il 2010?"* ("Which movies did Christopher Nolan direct after 2010?") and get the SQL query plus the results. The interface and the prompts are in Italian.
- **Self-correcting retry.** If the first query is invalid or fails, the error message is fed back to the LLM together with the schema, and a second, corrected query is attempted.
- **Read-only guard.** Only `SELECT` statements are executed. Anything that could modify the database (`INSERT`, `UPDATE`, `DELETE`, `DROP`, …) is rejected before reaching MariaDB.
- **Schema-aware prompts.** The current database schema is read from `INFORMATION_SCHEMA` and included in every prompt, so the model only uses tables and columns that exist.
- **Manual SQL console** and a form to **add or update a movie** (director, year, genre, streaming platforms).
- **Automatic data loading.** On first start the backend imports `data.tsv` into a normalised schema.

## Architecture

Four services, orchestrated with Docker Compose and started in the right order through health checks:

```
 Browser ──► frontend (FastAPI + Jinja2, :8004)
                 │  REST
                 ▼
             backend (FastAPI, :8003) ──► Ollama (Gemma 3 1B, :11434)
                 │
                 ▼
             MariaDB 11 (:3306)
```

| Service | Role |
|---|---|
| `frontend` | Web interface rendered with Jinja2 templates; forwards every action to the backend |
| `backend` | REST API: prompt building, LLM calls, SQL validation and execution, data import |
| `ollama` | Runs the Gemma 3 model locally; the models are pulled automatically on first start |
| `mariadb` | Stores the data; the schema is created by `mariadb_init/init.sql` |

### Database schema

`directors` (name, age) · `movies` (title, year, genre, director) · `platforms` (name) · `movie_platform` (many-to-many link between movies and platforms)

### Backend API

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/ping` | Health check |
| `GET` | `/schema_summary` | Tables and columns of the database |
| `POST` | `/search` | Natural-language question → SQL → results |
| `POST` | `/search_with_retry` | Same as `/search`, with an automatic correction attempt |
| `POST` | `/sql_search` | Runs a SQL `SELECT` written by hand |
| `POST` | `/add` | Adds or updates a movie from a comma-separated line |

Example request:

```bash
curl -X POST http://localhost:8003/search \
     -H "Content-Type: application/json" \
     -d '{"question": "Quali film sono usciti nel 2010?"}'
```

## Getting started

Requirements: Docker and Docker Compose.

```bash
git clone https://github.com/Pmax8/text-to-sql-llm.git
cd text-to-sql-llm
docker compose up --build
```

The first start takes a few minutes because Ollama downloads the model. Then open:

- Web interface: http://localhost:8004
- Backend API docs (generated by FastAPI): http://localhost:8003/docs

### Tests

The course's automated test suite runs from outside Docker against the backend:

```bash
pip install requests
python test_backend_progetto_finale.py --group-size 3
```

## Known limitations and next steps

- The read-only guard works on keywords, so it can also reject harmless queries that merely contain a word like `update` inside a string. A SQL parser or a read-only database user would be more precise.
- Database credentials are written in `docker-compose.yaml` for local use; they should move to a `.env` file.
- A 1B-parameter model is fast but makes mistakes on complex questions with several joins; the retry mechanism mitigates this.
